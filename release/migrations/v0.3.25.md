# v0.3.25 upgrade guidance

Stable upgrades are supported by the manifest; downgrade is unsupported and
recovery is forward-fix. No alpha promotion revisions are declared. Review crossed
release instructions when upgrading from before v0.3.24, including its ContextForge
credential preparation and ownership handoff. Existing prerequisites remain unchanged.

## PII Engine

Engine and model-sync now use the same verified `0.13.0` image without a CPU/CUDA
tag suffix. Remove obsolete `monitorPiiEngine.device` and `accelerator` settings;
the Engine runs on CPU, while remote inference services manage their own hardware.
Generic CPU/memory resources, node selectors and tolerations remain supported.

Leaving `monitorPiiEngine.ner` absent or null retains legacy selection. To opt in,
first reconcile this compatible Base release, then select the reviewed `ner` block
in client values. Replace non-default legacy backend, remote-model and policy NER
selectors rather than combining them with canonical selection. Local, remote and
disabled NER modes all retain CPU rules, custom recognizers and policy enforcement.

Local profiles use the bundled language models. Remote profiles require approved
endpoints, model identities and exact network egress; private HTTP requires explicit
approval and isolation. KServe profiles also require their verified tokenizer assets.
The optional inference-runtime-manager NER recipes are available from Tooling commit
`bc9be6d0f47bb23369c2f45dc321c932e2dbcac3`; existing compatible remote services do
not need reinstalling. Keep existing model caches, PVCs and model-sync resources.
After activation, verify Engine readiness, selected language/model assignments,
remote connectivity where selected and bounded logs without exposing request content.

## MCP workflows

Studio API and Web advance to `0.16.3`. Named operator discovery remains opt-in;
configure the same approved subject/email binding in ContextForge and Studio only
after this release is applied. Ordinary personal connections retain their current
configuration. Discovery uses the named operator's own consent; publication remains
a separate authorized setup operation. Verify publication status and approved-tool
checks before considering a newly discovered provider ready.

Preserve ContextForge's database and matching encryption keys, confirm current
independent backups, and follow the chart's existing migration/startup ordering.
After adoption, check Flux sources, Kustomizations, HelmReleases, affected application
health, persistent-state availability, warning events and bounded logs.
