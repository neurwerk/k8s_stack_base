# Platform v0.2.4

## Support

- Fresh installation: Supported.
- Supported source versions: `v0.2.0`, `v0.2.1`, `v0.2.2`, `v0.2.3`.
- Upgrade from `v0.1.0` through `v0.1.3`: Unsupported.
- Upgrade from unversioned `main`: Unsupported.
- Downgrade: Unsupported.

This patch makes Dify's non-transactional PostgreSQL index migration safe to
retry, bounds LibreChat's shared DocumentDB connection fan-out, and constrains
AgentGateway model-catalog rates to the precision accepted by its data plane.

## Prerequisites

Install the exact CRD and controller prerequisites listed in
`release/manifest.yaml`. Continue to use `stack-setup` package `0.2.10` from
reviewed tooling commit
`fbf91a133e755e5f5b3a79e0e73c2506fc09021f`.

Verify that
`ghcr.io/neurwerk/addon-dify-ce-builder-api:1.15.0-kc-v13` provides a
`linux/amd64` manifest before rollout.

## Client Actions

Set `GitRepository/k8s-stack.spec.ref.tag` to `v0.2.4` while retaining
`verify.mode: Tag` and the existing `k8s-stack-release-trust` reference.

Required client value changes: None.

Required confidential value changes: None.

## Stateful And API Effects

Dify API image `1.15.0-kc-v13` preserves upstream migration revision
`4474872b0ee6` and its intended schema. If an earlier attempt left the exact
valid `workflow_node_executions_tenant_id_idx` before Alembic recorded the
revision, the retry reuses it and continues. An invalid same-name remnant is
replaced; a valid conflicting definition fails closed. A fresh installation
creates the same index and nullable `workflow_draft_variables.node_execution_id`
column as upstream Dify `1.15.0`. An installation that already completed the
migration does not rerun it.

The image pin applies to Dify API, worker, and beat. The Dify web image and
application version remain unchanged.

LibreChat now caps its DocumentDB pool at 20 connections and concurrent
connection establishment at two. This changes runtime connection bounds only;
it does not change credentials, schemas, APIs, or stored conversations.

AgentGateway's reviewed model rates are rounded to no more than six fractional
digits. This is pricing-catalog precision enforcement, not a model identity,
authorization, routing, or provider change.

## Pre-Deployment Checks

1. Verify the expected cluster context and stable cluster identity.
2. Verify the signed `v0.2.4` tag and generated release manifest.
3. Verify the Dify API `1.15.0-kc-v13` amd64 image exists and differs from the
   superseded `1.15.0-kc-v11` and byte-identical `1.15.0-kc-v12` images.
4. For a failed Dify bootstrap, retain the Dify PostgreSQL database and allow
   the patched migration to reconcile the index; do not stamp Alembic or edit
   the index manually.
5. Confirm the client retains tag-signature verification and the existing
   release trust reference.

## Post-Deployment Checks

Inspect both Git sources, all Flux Kustomizations, all HelmReleases, warning
events, and affected logs. Confirm the Dify migration Job succeeds, Dify API,
worker, beat, and web HelmReleases become Ready, the Dify Gateway reports
`Programmed=True` and `ResolvedRefs=True`, its certificate becomes Ready, and
the public HTTPS endpoint responds without an SNI error.

Confirm LibreChat remains Ready with the bounded DocumentDB pool and
AgentGateway no longer rejects its merged catalog for excessive decimal
precision.

## Recovery

Recovery classification: Replacement restore.

A Git declaration revert is not a state rollback. Do not manually stamp Alembic
or remove a valid conflicting index if Dify fails closed; inspect the migration
metadata and publish a corrective patch. Follow the complete
replacement-restore procedure for unrecoverable stateful failure.

## Exclusions

- LibreChat RAG remains excluded until its deployment-readiness and effective
  render contracts are complete.
- LibreChat Code Interpreter remains excluded because its first-party runtime
  images have not been released.
