# Platform v0.2.2

## Support

- Fresh installation: Supported.
- Supported source versions: `v0.2.0`, `v0.2.1`.
- Upgrade from `v0.1.0` through `v0.1.3`: Unsupported.
- Upgrade from unversioned `main`: Unsupported.
- Downgrade: Unsupported.

This patch fixes DocumentDB application-user provisioning after the shared
operations database initializes. DocumentDB `0.116.0` accepts user-management
commands only through its `admin` authentication database. The `librechat` user
is now stored and authenticated there with the `readWriteAnyDatabase` and
`clusterAdmin` combination required for secondary write users. It does not
receive user-management authorization.

## Prerequisites

Install the exact CRD and controller prerequisites listed in
`release/manifest.yaml`. Continue to use `stack-setup` package `0.2.10` from
reviewed tooling commit
`fbf91a133e755e5f5b3a79e0e73c2506fc09021f`.

The amd64 node running `postgres-operations` must expose the complete
`x86-64-v3` CPU baseline. For Proxmox, use CPU type `x86-64-v3` or `host` and
apply the change with a complete VM stop and start. Verify that the guest exposes
`avx`, `avx2`, `bmi1`, `bmi2`, `f16c`, `fma`, `abm`, `movbe`, and `xsave`.

## Client Actions

Set `GitRepository/k8s-stack.spec.ref.tag` to `v0.2.2` while retaining
`verify.mode: Tag` and the existing `k8s-stack-release-trust` reference.

Required client value changes: None.

Required confidential value changes: None.

Retain `PersistentVolumeClaim/data-postgres-operations-0`. Do not delete or
replace the claim to recover a failed `v0.2.0` or `v0.2.1` installation. Rerun
`stack-setup bootstrap` after Flux observes the signed `v0.2.2` source; the
post-seed bootstrap checkpoint resumes downstream convergence.

## Stateful And API Effects

The DocumentDB identity is `admin.librechat`, authenticated with
`authSource=admin`, with `readWriteAnyDatabase` and `clusterAdmin` on `admin`.
This changes the failed attempted identity contract from `LibreChat.librechat`;
the pinned DocumentDB version rejects that user before creation. Existing
credentials and the retained PostgreSQL data directory remain unchanged.

LibreChat is the only permitted Mongo-compatible consumer of this DocumentDB
gateway. Do not add another application or logical Mongo database to the shared
gateway while this exception remains active; use a separate DocumentDB instance
for another consumer. The broad DocumentDB role does not grant access to the
Dify, Langfuse, or LibreChat RAG PostgreSQL databases, whose separate login and
database grants remain enforced and are verified by the provisioning gate.

The provisioning gate verifies the exact user metadata and performs a temporary
authenticated write, read, delete, and collection cleanup in `LibreChat`. It
fails the Helm release if authentication or authorization is incomplete.
The hook grants `operations_admin` PostgreSQL `CREATEROLE` and temporary
`ADMIN OPTION` membership in `documentdb_admin_role` only while reconciling
the native user. After reconciliation, the database owner takes over the
application role grant before the hook revokes both temporary administrator
capabilities through an exit trap. The hook verifies the owner grant and both
revocations before succeeding.
Both shared PostgreSQL provisioning hooks use POSIX-compatible readiness
deadlines and retain separate failed retry Pods until their one-day Job TTL,
making a failed release gate diagnosable without changing its retry limit.

No other application database contract changes. Keycloak continues to use the
separate `postgres-auth` server. Dify, Langfuse, and LibreChat RAG continue to use
their existing PostgreSQL roles and databases on port 5432.

## Pre-Deployment Checks

1. Verify the expected cluster context and stable cluster identity.
2. Verify the signed `v0.2.2` tag and generated release manifest.
3. Confirm the node exposes the complete `x86-64-v3` CPU baseline.
4. Confirm the existing operations PVC is retained and bound.
5. Retain the completed OpenBao custody kit and incomplete bootstrap checkpoint.

## Post-Deployment Checks

Inspect both Git sources, all Flux Kustomizations, all HelmReleases, warning
events, and affected logs. Confirm the `postgres-operations-provision` Job
succeeds on its initial attempt or retry, reports no unexpected PostgreSQL
database access for `librechat`, `postgres-operations` remains Ready, and
LibreChat starts with verified TLS to the DocumentDB gateway. Rerun
`stack-setup bootstrap` and confirm infrastructure and applications converge
without reading Secret values.

## Recovery

Recovery classification: Replacement restore.

A Git declaration revert is not a state rollback. If provisioning fails, retain
the PVC and correct the declarative contract. If unrelated stateful effects
occur, rebuild a separate empty environment and restore only through the complete
shared operations database recovery procedure.

## Exclusions

- LibreChat RAG remains excluded until its deployment-readiness and effective
  render contracts are complete.
- LibreChat Code Interpreter remains excluded because its first-party runtime
  images have not been released.
