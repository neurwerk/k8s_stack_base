# Platform v0.3.1

## Support

- Stable upgrades: Fresh installation only.
- Supported alpha source revisions: None.
- Downgrade: Unsupported.

Installation requires an independently verified empty or replacement environment.
No in-place stable upgrade or alpha promotion is supported. The signed predecessor
is `v0.3.0`; included implementation ends at
`1ee6085519f8f6898cb1f2bd6dd6cf9bc18da0e1` (routing PR #70).

## Prerequisites

- Independently verify and record that the target is empty or is a replacement
  environment and that installation will not overwrite existing persistent state.
  A statement that existing data is disposable is not empty-target verification.
  Neither this release nor its preparation authorizes deleting resources or data.
- After separate signing and publication, verify the exact target tag and the
  independently authenticated platform signer. Provision public
  `k8s-stack-release-trust` outside Git.
- Install every exact prerequisite in `release/manifest.yaml`, unchanged from
  `v0.3.0`: Flux 2.9.4, openbao-stack-setup 0.2.11 at tooling commit
  `5d1a33a938e22e9034581aebecf33485adc88a29`, Gateway API experimental 1.6.0,
  cert-manager CRDs 1.20.2, Prometheus Operator chart/CRDs 72.4.0,
  AgentGateway CRDs 1.5.0, External Secrets CRDs 2.9.0, and the DocumentDB
  x86-64-v3 CPU baseline. Do not downgrade existing APIs or reuse state as an
  undocumented upgrade shortcut.
- Verify successful schema-4 reconciliation with the exact declared
  openbao-stack-setup tool before enabling AgentGateway usage storage. The tool
  does not migrate application databases or authorize a platform transition.
- Stage the required client-owned model catalog, pricing, Dify default, local
  fallback, roles, storage, certificates, and externally delivered secrets.

## Client Actions

These instructions require separate client adoption and deployment approval:

1. Render the complete client composition. Stage the routing mode in client
   values consumed by Dify API, LibreChat app, and Keycloak initial-admin before
   platform adoption. Use `public-dns` for public canonical endpoint resolution;
   use `internal-traefik` only with the reviewed internal-routing plan.
2. After publication and independent empty/replacement-target verification,
   select exact signed tag `v0.3.1` with Flux tag verification and
   `k8s-stack-release-trust`. Set
   `platform.neurwerk.com/adoption-target: v0.3.1` and
   `platform.neurwerk.com/adoption-mode: fresh-install`. Do not use `upgrade`.
3. For internal routing, reconcile and verify the new NetworkPolicies before
   separately adding exact CoreDNS rewrites for the reviewed names. Never use
   wildcard or parent-zone rewrites. Client and platform sources are not atomic.

## Breaking Changes

- `canonicalEndpointRouting.mode` defaults to `internal-traefik`. Unknown modes
  fail Helm rendering. Public DNS clients must explicitly set `public-dns`.
- The Keycloak action-email Job defaults to selected Traefik Pod egress on TCP
  `443` instead of general public HTTPS. Without aligned DNS and values, issuer
  readiness and action-email delivery can fail. Dify API and LibreChat retain
  their existing public HTTPS allowances in both modes.
- Existing `v0.3.0` client-owned model-catalog, pricing, Dify default, local
  fallback, and authorization requirements still apply to fresh installations.

## Stateful And API Effects

Fresh installation creates configured Kubernetes, PostgreSQL, object, and
secret-backed application state. No existing state migration is claimed.
AgentGateway usage records remain persistent operations PostgreSQL state.

Relative to `v0.3.0`, the routing change advances three chart versions from
`1.0.1` to `1.0.2` and updates routing defaults and NetworkPolicies. It changes no
application image, database schema, CRD, Kubernetes identity, or persistent volume.
This limited delta does not establish an in-place upgrade contract.

Exact Pod DNS rewrites are cluster-wide for matching names, not workload scoped.
Canonical URLs, TLS SNI, OIDC issuer identity, redirects, and S3 signatures must
remain unchanged. Standard NetworkPolicy cannot restrict TLS SNI or HTTP Host on
the shared Traefik listener. A compromised allowed workload can attempt other
routes; application authentication and authorization remain required.

## Pre-Deployment Checks

1. Record independent empty/replacement-target verification and confirm no
   existing persistent state will be overwritten. Stop if this is unverified.
2. Verify the published signed tag, release manifest, migration document, image
   pins, prerequisites, exclusions, and exception expiry dates.
3. Run `make check` and `make release-check` and render the complete client
   composition, including catalogs, pricing, routing mode, and access grants.
4. Verify storage classes, DNS answers, Traefik selectors and reachability,
   certificates, OpenBao providers, and externally provisioned trust material.
5. Confirm excluded optional packages are not composed. If applicable backups
   will be restored into a replacement, verify them independently with the
   component's supported restore and integrity checks before use.

Rendered routing tests cover both modes and invalid-mode rejection. No live
installation, transition, restore, or recovery was performed during preparation;
offline validation does not prove target emptiness or application data integrity.

## Post-Deployment Checks

After separately authorized deployment, record the exact applied revisions and:

1. Verify the Flux source resolves to signed tag `v0.3.1`, all required
   Kustomizations and enabled HelmReleases are Ready, and inspect warning events
   and affected logs without secret values or sensitive request data.
2. Verify affected policies select only the intended Traefik Pods on TCP `443`
   in internal mode, and omit the added allowance in public mode.
3. Verify exact rewritten DNS names and unrelated answers, strict HTTPS,
   Gateway/HTTPRoute acceptance and references, certificates, unchanged OIDC
   issuer identity, Dify and LibreChat authentication, and Keycloak action email.
4. Verify PostgreSQL, object storage, secret synchronization, LibreChat signed
   S3 requests, model authorization, streaming requests, and Studio usage
   attribution before making the environment available. Controller readiness
   alone does not prove application readiness or data usability.

## Recovery

Recovery classification: Replacement restore.

If installation fails or integrity is uncertain, keep the failed target
unavailable and preserve redacted failure evidence. After separate operational
approval, prepare an independently verified replacement environment from reviewed
configuration. Re-provision external trust and secret material through documented
custody procedures. Restore any applicable independently verified backups using
the component's supported tooling and order, then repeat all pre- and
post-deployment checks and application integrity checks before use. When no state
is to be restored, repeat fresh installation into the verified replacement.

This classification matches the predecessor's fresh-install recovery approach;
it does not claim a tested restore was performed during preparation. A Git revert
does not restore database, object, Kubernetes, or secret state. Do not downgrade
CRDs or application data. Retained PVCs and in-cluster snapshots are not
independent backups. Disposal of a failed environment or existing data requires
separate explicit authorization; this document grants none.

## Exclusions

- Stable upgrades, alpha promotion, and all downgrades are unsupported.
- LibreChat RAG and Code Interpreter remain excluded from the release packages.
- Existing immutable LibreChat development-image and DocumentDB privilege
  exceptions retain their manifest owners and expiry dates (2026-09-30 and
  2026-11-27 respectively); this release does not renew or broaden them.
- K3s/control-plane upgrades, credential provisioning, cluster access, DNS
  changes, client adoption, deployment, tagging, and publication are outside
  this preparation. No live evidence is implied by these instructions.
