# v0.3.24 upgrade guidance

ContextForge becomes a default Base component, with private TLS and encrypted
database-backed OAuth storage. Context7, Brave and GitHub presets are available
but disabled by default. Provider selection, credentials, trusted-proxy identity,
Studio origin, setup Job and access grants remain explicit configuration.
Vault OAuth storage is not supported until the upstream integration is ready.

## Preparation

Use `openbao-stack-setup` `0.2.26` from the exact Tooling source in the manifest.
Reconcile the approved ContextForge credential catalog without rotating existing
values. The prerequisite CLI still selects this catalog through
`contextforge.enabled: true` and an operator-approved
`contextforge.platformAdminEmail` in the namespace-local
`contextforge-product-values` ConfigMap. These prepare the Base service, not MCP
provider selections; an installation without existing credentials must supply
them before reconciliation. Verify `contextforge-runtime` in `contextforge` and
`contextforge-postgres-values` in `infra-postgres-operations` are Ready before
the infrastructure and applications stages reconcile. The default standalone
credential package is `releases/contextforge/secret-sync/database`; do not compose
it with `releases/contextforge/secret-sync`. A Vault OAuth token is not required.

Back up the operations database and retain its matching `AUTH_ENCRYPTION_SECRET`.
Never recreate the database or replace its encryption key to fix an upgrade.
Stop an existing ContextForge application before its migration hook runs; the
hook must complete before the application starts again. Verify the certificates,
database provisioner and application readiness after adoption.

## Existing standalone ContextForge stages

Before switching the platform source, inspect the actual Flux inventory. The
default namespace stage now owns `releases/namespaces/contextforge`; infrastructure
owns `releases/contextforge/postgres` and `releases/contextforge/certificates`;
applications owns `releases/contextforge/configuration` and
`releases/contextforge/app`. Credential delivery remains a separately ordered
Flux stage before infrastructure and applications.

For resources already owned by standalone Flux Kustomizations, disable pruning
on the old owners and wait for that change to reconcile before removing their
resource references. Reconcile the new default owners, verify their inventories
and Ready conditions, then retire the old empty stages. Keep a single active
owner throughout the handoff; do not delete namespaces, HelmReleases, Secrets,
database contents or encryption keys. Preserve existing product ConfigMaps and
provider selections. Provider OAuth application Secrets remain a separately
selected package and are not needed when all MCP providers are disabled.

## Remote NER

PII Engine `0.12.0-cpu` supports `remote-gliner` and `remote-kserve`; `local`
remains the default. Before selecting remote inference, approve model endpoints,
Secret references, exact destination CIDRs and ports. KServe also needs verified,
checksum-pinned tokenizer-only assets on the configured read-only PVC. Remote
NER has no local NER fallback; it retains local pattern/custom recognition and
the Engine's policy and anonymization behavior.

Publication does not authorize adoption or deployment. Stable upgrades follow
the manifest; downgrade is unsupported and recovery is forward-fix.
