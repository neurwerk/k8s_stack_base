# Platform v0.2.5

## Support

- Fresh installation: Supported.
- Supported source versions: `v0.2.0`, `v0.2.1`, `v0.2.2`, `v0.2.3`,
  `v0.2.4`.
- Upgrade from `v0.1.0` through `v0.1.3`: Unsupported.
- Upgrade from unversioned `main`: Unsupported.
- Downgrade: Unsupported.

This patch makes Dify's UUIDv7 helper migration compatible with PostgreSQL 18.

## Prerequisites

Install the exact CRD and controller prerequisites listed in
`release/manifest.yaml`. Continue to use `stack-setup` package `0.2.10` from
reviewed tooling commit
`fbf91a133e755e5f5b3a79e0e73c2506fc09021f`.

Verify that
`ghcr.io/neurwerk/addon-dify-ce-builder-api:1.15.0-kc-v14` provides a
`linux/amd64` manifest before rollout.

## Client Actions

Set `GitRepository/k8s-stack.spec.ref.tag` to `v0.2.5` while retaining
`verify.mode: Tag` and the existing `k8s-stack-release-trust` reference.

Required client value changes: None.

Required confidential value changes: None.

## Stateful And API Effects

Dify API image `1.15.0-kc-v14` preserves upstream migration revision
`1c9ba48be8e4`. On PostgreSQL 18, the migration reuses the native
`pg_catalog.uuidv7` implementation instead of creating an ambiguous public
overload. It still creates Dify's `public.uuidv7_boundary(timestamptz)` helper.
Its downgrade is restricted to explicit `public` signatures and cannot remove
PostgreSQL's native function.

The prior retry-safe behavior for revision `4474872b0ee6` remains unchanged. A
failed bootstrap may rerun both migrations without a manual function, index, or
Alembic repair. The image pin applies to Dify API, worker, and beat. The Dify
web image and application version remain unchanged.

## Pre-Deployment Checks

1. Verify the expected cluster context and stable cluster identity.
2. Verify the signed `v0.2.5` tag and generated release manifest.
3. Verify the Dify API `1.15.0-kc-v14` amd64 image exists and differs from the
   superseded `1.15.0-kc-v13` image.
4. For a failed Dify bootstrap, retain the Dify PostgreSQL database and allow
   the patched migrations to reconcile; do not stamp Alembic or edit functions
   or indexes manually.
5. Confirm the client retains tag-signature verification and the existing
   release trust reference.

## Post-Deployment Checks

Inspect both Git sources, all Flux Kustomizations, all HelmReleases, warning
events, and affected logs. Confirm the Dify migration Job succeeds, the Alembic
revision advances beyond `1c9ba48be8e4`, Dify API, worker, beat, and web
HelmReleases become Ready, the Dify Gateway reports `Programmed=True` and
`ResolvedRefs=True`, its certificate becomes Ready, and the public HTTPS
endpoint responds without an SNI error.

## Recovery

Recovery classification: Replacement restore.

A Git declaration revert is not a state rollback. Do not manually stamp Alembic
or add, remove, or replace UUID functions if Dify fails; preserve the migration
evidence and publish a corrective patch. Follow the complete
replacement-restore procedure for unrecoverable stateful failure.

## Exclusions

- LibreChat RAG remains excluded until its deployment-readiness and effective
  render contracts are complete.
- LibreChat Code Interpreter remains excluded because its first-party runtime
  images have not been released.
