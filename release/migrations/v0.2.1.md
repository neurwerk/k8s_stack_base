# Platform v0.2.1

## Support

- Fresh installation: Supported.
- Supported source versions: `v0.2.0`.
- Upgrade from `v0.1.0` through `v0.1.3`: Unsupported.
- Upgrade from unversioned `main`: Unsupported.
- Downgrade: Unsupported.

This patch fixes the first initialization of `postgres-operations` on the RBD
filesystem used by `v0.2.0`. The filesystem mount root contains `lost+found`,
which the DocumentDB entrypoint correctly rejects as a nonempty PostgreSQL data
directory. `v0.2.1` initializes PostgreSQL below that mount root instead.

## Prerequisites

Install the exact CRD and controller prerequisites listed in
`release/manifest.yaml`. Continue to use `stack-setup` package `0.2.10` from
reviewed tooling commit `fbf91a133e755e5f5b3a79e0e73c2506fc09021f`.

## Client Actions

Set `GitRepository/k8s-stack.spec.ref.tag` to `v0.2.1` while retaining
`verify.mode: Tag` and the existing `k8s-stack-release-trust` reference.

Required client value changes: None.

Required confidential value changes: None.

Retain `PersistentVolumeClaim/data-postgres-operations-0`. Do not delete or
replace the claim to recover the failed `v0.2.0` installation. Rerun
`stack-setup bootstrap` after Flux observes the signed `v0.2.1` source; the
post-seed bootstrap checkpoint resumes the downstream convergence phase.

## Stateful And API Effects

The operations PostgreSQL data directory moves from the RBD filesystem mount
root `/data` to `/data/postgresql` within the same retained PVC. A failed
`v0.2.0` fresh installation has no PostgreSQL cluster at `/data`; filesystem
metadata at the mount root is retained and ignored by the database entrypoint.

No API, credential, role, database, or PVC contract changes. This patch does not
add support for migrating `v0.1.x` application or database state.

## Pre-Deployment Checks

1. Verify the expected cluster context and stable cluster identity.
2. Verify the signed `v0.2.1` tag and generated release manifest.
3. Confirm `v0.2.0` is selected and `HelmRelease/postgres-operations` failed
   before database initialization with the nonempty data-directory diagnostic.
4. Confirm the existing operations PVC is retained and bound.
5. Retain the completed OpenBao custody kit and incomplete bootstrap checkpoint.

## Post-Deployment Checks

Inspect both Git sources, all Flux Kustomizations, all HelmReleases, warning
events, and affected logs. Confirm `postgres-operations` initializes under
`/data/postgresql`, its provisioning Job succeeds, and the StatefulSet becomes
Ready. Rerun `stack-setup bootstrap` and confirm infrastructure and applications
converge without reading Secret values.

## Recovery

Recovery classification: Replacement restore.

A Git declaration revert is not a state rollback. If initialization fails before
the PostgreSQL cluster is created, retain the PVC and publish a corrective patch.
If unrelated stateful effects occur after initialization, rebuild a separate
empty environment and restore only through the complete shared operations
database recovery procedure.

## Exclusions

- LibreChat RAG remains excluded until its deployment-readiness and effective
  render contracts are complete.
- LibreChat Code Interpreter remains excluded because its first-party runtime
  images have not been released.
